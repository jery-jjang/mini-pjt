# 미니 PJT: 취약점 감시 Agent (VulnWatch)

> 교육 과정 Mini PJT입니다. 팀, 계정, 프로젝트, 메일 주소는 모두 교육용 더미 데이터이고, 취약점 데이터는 NVD·OSV·CISA KEV 공개 자료의 고정 사본입니다.

## 무엇을 푸나

프로젝트에서 쓰는 OS·미들웨어·라이브러리에 심각한 취약점이 새로 나와도 누가 언제 확인할지 정해져 있지 않아 늦게 알게 되는 문제를, 제품과 버전을 한 번 등록해 두면 해당하는 취약점을 판정해 주고 심각한 것만 프로젝트별로 알려 주는 Agent로 풉니다.

기획 전체는 [SERVICE.md](SERVICE.md)에 있습니다.

## 활용한 패턴 (Day 1~7)

| # | 패턴 | Day | 어떻게 활용했나 |
|---|---|---|---|
| 1 | LCEL chain (Pydantic 구조화 출력) | Day 1 | `프롬프트 \| 모델.with_structured_output(...)` 체인 네 곳: 등록 문장의 식별자 후보 제시(`src/tools.py`), 문서 검색의 쿼리 확장(`src/retriever.py`), 알림 메일의 취약점 요약(`src/notifier.py`), 평가의 LLM 채점(`evaluation/run_eval.py`) |
| 2 | ReAct (도구 자율 선택) | Day 3 | `create_agent`에 도구 7개를 붙여 모델이 질문에 맞는 도구를 고른다(`src/agent.py`) |
| 3 | RAG (하이브리드 검색·쿼리 확장) | Day 2 | 취약점 레코드 20건(참고 링크, 점수, KEV 여부, 영향 버전 범위, 설명문)을 검색해 답의 근거로 쓰고 `contexts`에 싣는다. 참고 링크는 ID로 코드가 만든 NVD·OSV·GitHub Advisory·CISA KEV 주소다. ① 질문의 CVE·GHSA ID는 정확 일치로 먼저 찾고, ② 한글 검색어는 모델이 영어 키워드로 넓히고(구조화 출력), ③ BM25 키워드 검색과 Titan 임베딩 의미 검색의 순위를 RRF로 합친다. 의미 검색은 유사도 0.2 미만을 버려 무관한 질문에는 문서를 내놓지 않는다(`src/retriever.py`). 리랭킹은 하지 않았다 |
| 4 | 도구 다중 | Day 4 | SQLite(등록·현황), 버전 판정 코드, 문서 검색, 검색 실행을 각각 도구로 만들었다(`src/tools.py`). "사내 포털의 Nginx 취약점 중 mp4 모듈 관련 건을 설명해줘"(28번)처럼 해당 여부 조회와 문서 검색을 한 질의에서 함께 쓴다. 다만 2차 평가에서 도구를 2개 이상 쓴 질의는 이 1건이고, 외부 API 도구는 없다 |
| 6 | 가드레일 | Day 5 | 다른 팀 데이터 차단과 '근거 없음' 판정은 코드가 한다. 공격 방법·지시 조작·무관한 질문은 모델이 거절 도구를 불러 기록한다. 모델에 보내는 글에서는 프로젝트명과 팀명을 가린다 |
| 8 | 미들웨어 | Day 5 | `create_agent`에 미들웨어 두 개를 붙였다(`src/agent.py`). ① 재시도: Bedrock이 다시 시도할 만한 오류(모델이 도구 호출 형식을 잘못 만든 `ModelErrorException`, 일시적인 서버 오류)를 내면 잠시 기다렸다가 최대 2번 다시 부른다. temperature 0에서는 같은 잘못된 호출이 되풀이돼 기본 `ModelRetryMiddleware`로는 풀리지 않아, 다시 부를 때만 temperature를 0.7로 올린다. 하루 한도 초과는 다시 불러도 소용없어 재시도하지 않는다. Nova Pro가 답 대신 콘텐츠 필터 차단 문구를 돌려줄 때도 같은 방식으로 다시 부른다(1차의 18번). ② 이름 가리기 안전망: 모델에 보내는 메시지 전체를 한 번 더 가려, 도구 하나가 가리기를 빠뜨려도 모델에는 가린 글만 간다 |
| 11 | Observability · Trace | Day 7 | LangSmith에 요청마다 `vulnwatch-query` 실행으로 모델 호출과 도구 호출을 남긴다(알림 요약은 `vulnwatch-alert-summary`). 같은 `run_id`로 응답의 `trace`와 로컬 파일 `var/traces.jsonl`에도 남겨 둘을 잇는다. 모델에 보내기 전에 프로젝트명·팀명을 가리므로 LangSmith에도 가린 글만 남는다(`src/agent.py`) |
| 12 | 평가 (RAGAS · LLM-as-Judge) | Day 7 | 인-아웃 세트 30건을 코드 채점(해당 여부 문항은 ID 정확 일치)과 LLM 채점으로 평가하고(`evaluation/run_eval.py`), RAGAS 네 지표를 낸다(`evaluation/run_ragas.py`) |

쓰지 않은 패턴과 이유:

- **5 MCP, 9 Multi-Agent, 10 Plan-Execute·장기 메모리**: 질문 하나에 도구 한두 개로 끝나는 작업이라 필요하지 않았습니다.
- **7 HITL**: LangGraph의 `interrupt()`는 쓰지 않았습니다. 대신 등록은 "후보 제시 → 사람이 번호로 확정"의 두 번 요청으로 나눠, 사람이 확정하기 전에는 반영되지 않게 했습니다.
- **8 미들웨어 중 이름 가리기 자체**: 질문과 도구 결과를 가리는 일은 미들웨어로 옮기지 않았습니다. 미들웨어는 에이전트와 도구 실행 안쪽에서 돌아서, 거기서 가리면 LangSmith에 기록되는 에이전트 입력과 도구 출력에는 가리기 전 이름이 남기 때문입니다. 그래서 질문은 에이전트 실행 전에, 도구 결과는 도구 안에서 가리고, 미들웨어는 모델 앞의 안전망으로만 씁니다. 대화 요약 미들웨어는 요청마다 대화가 새로 시작돼 요약할 이력이 없어 쓰지 않았습니다.

LangSmith 추적은 `.env`의 `LANGSMITH_TRACING=true`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT`로 켭니다. 실제 질문 하나의 LangSmith 기록을 읽어, 프로젝트명·팀명·수신 주소·토큰이 0번 나오고 `[프로젝트2]`, `[팀1]` 같은 가린 표시만 남는 것을 확인했습니다. 자동 테스트는 추적을 끄고 돌아 외부로 아무것도 보내지 않습니다.

## 아키텍처

```
사용자 ──POST /query {"question"}──▶ app.py (FastAPI)
                                      │  토큰으로 계정 확인 (src/auth.py). 토큰이 없으면 팀 A 팀원
                                      ▼
                               src/agent.py
                                 1. 프로젝트명·팀명을 [프로젝트1] 같은 표시로 가림
                                 2. create_agent (Bedrock Amazon Nova Pro) 가 도구 선택
                                 3. 답변에서 표시를 원래 이름으로 되돌림
                                 4. 라벨을 코드로 결정 (answer / no_answer / guardrail)
                                      │
        ┌──────────────┬──────────────┼───────────────┬──────────────┬─────────────┐
        ▼              ▼              ▼               ▼              ▼             ▼
  propose_candidates  check_         get_project_   search_vuln_   run_scan_now  refuse_
  confirm_registration vulnerabilities status         docs                         request
   (등록 두 단계)     (해당 여부)    (현황)         (문서 검색)    (검색 1회)    (거절 기록)
        │              │              │               │              │
        │              └──── src/matching.py ◀────────┼──────────────┤   버전 범위 비교, 점수 출처,
        │                    (일반 코드, LLM 없음)    │              │   알림 대상 판정
        ▼                                             ▼              ▼
  src/storage.py (SQLite)                   src/retriever.py   src/scheduler.py ──▶ src/notifier.py
  등록 항목, 대기 후보, 알림 이력, 메일     (ID 일치+BM25·임베딩) (6시간 주기)     메일을 DB(mails)에 저장
                                                  ▲                  ▲
                                                  └── src/sources.py ┘  data/vulns_t1.json, vulns_t2.json
```

역할 나눔:

- **코드가 하는 일**: 취약점 해당 여부 판정, 알림 발송 결정, 다른 팀 데이터 차단, 응답 라벨 결정.
- **모델이 하는 일**: 질문 의도 파악과 도구 선택, 답변 문장 작성, 등록 문장의 식별자 후보 제시, 알림 메일의 취약점 요약, 정책상 거절할 요청 가려내기.
- **모델에 보내지 않는 것**: 팀명, 프로젝트명, 수신 주소. 제품명·버전과 공개 취약점 정보만 보냅니다.

응답 형식(`POST /query`):

```json
{
  "answer": "근거 기반 응답",
  "contexts": [{"doc_id": "CVE-2021-44228", "text": "..."}],
  "trace": [{"step": "check_vulnerabilities", "input": "...", "output": "..."}],
  "label": "answer | no_answer | guardrail",
  "cve_ids": ["CVE-2021-44228"],
  "tools_called": ["check_vulnerabilities"]
}
```

`answer`, `contexts`, `trace`는 과정의 표준 규약이고, 나머지 세 키는 채점용으로 더한 것입니다.

답을 만들지 못하면 위 형식 대신 HTTP 오류 코드와 `{"detail": "이유"}`를 돌려줍니다.

| 코드 | 경우 |
|---|---|
| 401 | 모르는 토큰 |
| 422 | `question`이 없거나 비어 있음 |
| 429 | 모델(Bedrock) 호출 한도 초과. 계정의 하루 토큰 한도에 걸리면 이 오류가 납니다 |
| 503 | 그 밖의 모델 호출 실패(자격 증명, 연결 등) |

## 실행 방법

Python 3.14, Windows 기준입니다. 개발과 평가는 로컬 venv로 했습니다. 클린 환경에서 다시 만들어 보려면 아래쪽 "Docker로 실행 (선택)"을 씁니다.

```
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

`.env` 파일에 Bedrock 자격 증명(`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`)과 쓸 모델을 넣습니다.

```
VULNWATCH_MODEL_ID=us.amazon.nova-pro-v1:0
VULNWATCH_REGION=us-east-1
```

모델 ID를 적지 않아도 Amazon Nova Pro(`us.amazon.nova-pro-v1:0`)를 씁니다. 아래 평가 결과(1차·2차 통과율, LLM 채점, RAGAS)는 모두 Nova Pro로 낸 것입니다. 모델을 바꾸면 도구 선택이 달라져 결과가 달라질 수 있습니다.

```
.venv\Scripts\python -m uvicorn app:app                    서버 실행. 화면은 http://127.0.0.1:8000/ui/
.venv\Scripts\python -m pytest tests -q                    자동 테스트 180건 (실제 LLM 호출 없음)
.venv\Scripts\python evaluation/run_eval.py --round 2      인-아웃 세트 30건 평가 (실제 Bedrock 호출. roundN_report.md를 덮어쓴다)
.venv\Scripts\python evaluation/run_ragas.py --round 2     RAGAS 지표 (run_eval 뒤에 실행. 설치 방법은 requirements.txt 아래쪽)
.venv\Scripts\python -m src.scheduler --snapshot T2        검색 1회 실행 (알림 메일은 DB에 저장)
.venv\Scripts\python -m src.notifier --list                저장된 알림 메일 목록 (--show N 으로 N번 본문)
.venv\Scripts\python -m src.storage --load-demo            로컬 DB에 시연용 등록 항목 19개 추가 (프로젝트마다 8~10개가 된다)
```

### Docker로 실행 (선택)

클린 환경에서 다시 만들어지는지 확인하기 위한 `Dockerfile`입니다. 이미지에는 코드와 교육용 더미 데이터만 넣고, `.env`와 `var/`는 넣지 않습니다.

```
docker build -t vulnwatch .
docker run --rm vulnwatch python -m pytest tests -q            자동 테스트 (실제 LLM 호출 없음)
docker run --rm -p 8000:8000 --env-file .env vulnwatch         서버 실행. 화면은 http://127.0.0.1:8000/ui/
```

Docker 29.9.3(Linux 컨테이너, Python 3.14.10)에서 이미지를 빌드해, 컨테이너 안에서 자동 테스트 180건 통과와 서버 기동(`/settings`, `/projects`, `/ui/` 응답)을 확인했습니다. 실제 질문은 Bedrock 자격 증명을 `--env-file`로 줘야 답합니다. RAGAS 평가에 필요한 패키지는 이미지에 넣지 않았습니다(`requirements.txt` 아래쪽 설치 방법 참고).

### 설정

`.env`에 적거나 환경 변수로 주면 서버가 뜰 때 읽습니다. 검색 주기와 취약점 데이터 시점은 아래 "검색 주기 바꾸기"처럼 서버를 띄운 채로 바꿀 수 있고, 나머지는 바꾼 뒤 서버를 다시 띄워야 합니다.

| 설정 | 기본값 | 내용 |
|---|---|---|
| `VULNWATCH_SCAN_INTERVAL_HOURS` | `6` | 주기 검색 간격의 처음 값(시간). 소수도 됩니다. 예: `1`(1시간), `0.5`(30분), `0.05`(3분). 0 이하나 숫자가 아닌 값이면 서버가 뜨지 않고 이유를 알려 줍니다 |
| `VULNWATCH_SCHEDULER_ENABLED` | `true` | `false`면 주기 검색을 하지 않습니다. 검색은 대화("지금 검색 실행해줘")나 위의 1회 실행 명령으로만 합니다 |
| `VULNWATCH_SNAPSHOT` | `T1` | 쓸 취약점 스냅샷 시점(`T1` 또는 `T2`)의 처음 값. 화면이나 API로 바꾸면 그 값이 우선합니다 |
| `VULNWATCH_ALERT_CVSS_THRESHOLD` | `9.0` | 알림 기준 점수 |
| `VULNWATCH_FAILURE_NOTICE_THRESHOLD` | `2` | 조회가 몇 회 연속 실패하면 보안 담당자에게 알릴지 |

주기 검색의 첫 실행은 서버가 뜬 시점이 아니라 한 주기가 지난 뒤입니다. 시연에서 알림을 바로 보려면 주기를 짧게 두거나(`0.005`면 약 18초), 대화로 "지금 검색 실행해줘"라고 요청합니다. 주기를 짧게 두면 알림이 생길 때마다 메일 요약에 모델을 부르므로 호출이 늘어납니다. 같은 데이터에서는 중복 알림이 없어 두 번째 주기부터는 호출하지 않습니다.

### 검색 주기 바꾸기 (서버 재시작 없이)

UI에서 쓸 수 있도록 API로 엽니다.

| 요청 | 권한 | 내용 |
|---|---|---|
| `GET /settings` | 누구나 | 현재 주기, 주기 검색 사용 여부, 마지막 검색 시각, 다음 검색 시각, 취약점 데이터 시점 |
| `PUT /settings/scan-interval` 본문 `{"hours": 1}` | 보안 담당자 토큰만 | 주기를 바꾸고 바뀐 상태를 돌려줍니다 |
| `PUT /settings/snapshot` 본문 `{"snapshot": "T2"}` | 보안 담당자 토큰만 | 취약점 데이터 시점(T1 또는 T2)을 바꿉니다. 다른 값은 422 |

```powershell
Invoke-RestMethod http://127.0.0.1:8000/settings/scan-interval -Method Put -ContentType "application/json" `
  -Headers @{ Authorization = "Bearer demo-token-security" } -Body '{"hours": 1}'
```

- **바로 반영됩니다.** 다음 검색은 바꾼 시각에서 새 주기만큼 뒤입니다. 예: 6시간 주기로 2시간이 지난 때 1시간으로 바꾸면 지금부터 1시간 뒤에 검색합니다.
- **유지됩니다.** 바꾼 주기는 DB에 저장되어 서버를 다시 띄워도 그 값을 씁니다. `.env` 값은 저장된 주기가 없을 때만 씁니다.
- **0 이하나 숫자가 아닌 값은 422**로 거부하고 주기를 바꾸지 않습니다. 팀원 토큰이나 토큰 없이 요청하면 403, 모르는 토큰은 401입니다.
- 주기는 모든 팀의 프로젝트에 한꺼번에 적용되어 보안 담당자만 바꿀 수 있게 했습니다.
- **취약점 데이터 시점**도 같은 창에서 바꿉니다. 실시간 조회 대신 두 시점의 고정 사본(T1, T2)을 쓰므로, 시점을 T2로 바꾸는 것이 "취약점 데이터가 갱신됐다"를 흉내 냅니다. 바꾼 뒤의 주기 검색, "지금 검색 실행해줘", 답변이 모두 그 시점을 쓰고, 바꾼 값은 DB에 저장됩니다. 시점을 바꿔도 검색을 바로 돌리지는 않습니다.

### 화면 (로컬 UI)

서버를 띄운 뒤 브라우저에서 `http://127.0.0.1:8000/ui/`를 엽니다(`http://127.0.0.1:8000/`도 이 화면으로 갑니다). 서버가 `web/`의 정적 파일을 내주므로 따로 설치하거나 빌드할 것이 없습니다.

- **계정**: 상단에서 팀 A 팀원, 팀 B 팀원, 보안 담당자 중 하나를 고릅니다. 로그인 화면 대신 데모 토큰 3개를 고르는 방식입니다.
- **등록된 SW**: 고른 계정이 볼 수 있는 프로젝트와 등록 항목을 보여 줍니다. 팀원은 자기 팀, 보안 담당자는 전체를 봅니다. 매핑이 확정되지 않은 항목은 '감시 불가'로 표시하고, 등록을 확정하면 목록이 바로 갱신됩니다. 항목 옆 휴지통 버튼을 누르면 확인 창을 거쳐 그 SW를 지웁니다(팀원은 자기 팀, 보안 담당자는 전체). 지운 SW는 감시와 알림에서 빠지고 알림 이력은 남으며, 같은 SW를 다시 등록하면 알림 조건에 따라 다시 알립니다. 삭제는 화면에서만 하고 대화로는 하지 않습니다.
- **질문**: 질문을 보내면 답변과 라벨(답변, 확인할 수 없음, 거절)을 보여 줍니다. 등록 후보가 나오면 번호 버튼으로 확정합니다. 오류(401, 422, 429, 503)는 이유를 대화 안에 보여 줍니다.
- **응답 상세**: 답변을 누르면 그 답변이 강조되고, 근거 문서(`contexts`)를 펼쳐 봅니다. 실행 기록(`trace`)은 보안 담당자 화면에만 보입니다(화면에서만 숨기며, `/query` 응답의 `trace`는 규약대로 그대로 채웁니다). 라벨과 취약점·도구 수는 답변 말풍선에 보입니다. 근거 문서는 SW 또는 CVE로 골라 봅니다. SW는 SW 하나에 걸린 CVE를 점수 높은 순으로 보고, CVE는 CVE 하나를 골라 점수, KEV, 영향 SW, 판정을 봅니다(SW 이름은 해당 여부 판정이 있으면 등록된 SW 이름, 없으면 데이터의 제품 이름). 근거 문서마다 원문을 확인할 수 있는 참고 링크(NVD, OSV, GitHub Advisory, CISA KEV)를 새 탭으로 엽니다.
- **알림함**: 상단의 알림함을 누르면 가짜 발송한 알림 메일(DB에 저장)의 목록과 본문을 봅니다. 버튼에는 안 읽은 메일 수가, 목록의 안 읽은 메일에는 N이 붙고, 메일을 열면 읽음이 됩니다(모두 읽음 버튼도 있습니다). 읽음 현황은 계정마다 따로이고, 보안 담당자는 메일마다 볼 수 있는 계정별로 읽었는지와 읽은 시각을 봅니다. 팀원은 자기 팀 프로젝트의 알림만, 보안 담당자는 조회 실패 통지를 포함해 전체와 받는 주소까지 봅니다.
- **검색 주기**: 상단의 검색 주기를 누르면 주기와 마지막·다음 검색 시각, 취약점 데이터 시점을 보고, 보안 담당자는 주기와 데이터 시점(T1/T2)을 바꿀 수 있습니다.

화면이 쓰는 등록 목록 API:

| 요청 | 권한 | 내용 |
|---|---|---|
| `GET /projects` | 토큰 기준(없으면 팀 A 팀원) | 계정이 볼 수 있는 프로젝트와 지우지 않은 등록 항목(항목 번호, 입력 문장, 표준 제품 이름, 버전, 감시 여부). 알림 수신 주소는 주지 않습니다. 모르는 토큰은 401 |
| `GET /mails`, `GET /mails/{mail_id}` | 팀원은 자기 팀 알림, 보안 담당자는 전체 | 알림함의 메일 목록(안 읽은 수 `unread_count`, 메일별 `read`)과 본문. 받는 주소와 계정별 읽음 현황(`readers`)은 보안 담당자에게만 줍니다. 모르는 토큰 401, 볼 수 없거나 없는 메일 404 |
| `POST /mails/{mail_id}/read`, `POST /mails/read-all` | 위와 같음 | 요청한 계정 기준으로 읽음 표시. 다른 계정의 읽음 현황은 바뀌지 않습니다 |
| `DELETE /projects/{project_id}/items/{item_id}` | 팀원은 자기 팀, 보안 담당자는 전체 | 등록한 SW 하나를 지웁니다(삭제 표시, 기록은 남김). 모르는 토큰 401, 다른 팀 403, 없거나 이미 지운 항목 404 |

질문을 API로 직접 보낼 수도 있습니다. 브라우저에서 `http://127.0.0.1:8000/docs`를 열어 `POST /query`를 실행하거나, PowerShell에서는 아래처럼 보냅니다.

```powershell
$body = [Text.Encoding]::UTF8.GetBytes('{"question": "Log4j 2.14.1에 해당하는 취약점이 뭐야?"}')
$r = Invoke-RestMethod -Uri http://127.0.0.1:8000/query -Method Post -ContentType "application/json" -Body $body
$r.answer
```

다른 계정으로 보낼 때는 `-Headers @{ Authorization = "Bearer demo-token-team-b" }`를 더합니다.

Windows에서 `curl -d "{...한글...}"`처럼 한글 질문을 명령줄에 직접 쓰면 인코딩이 깨져 서버가 400으로 거부합니다. `curl`을 쓰려면 질문을 UTF-8 파일로 저장해 `--data-binary @파일`로 보냅니다.

계정은 `Authorization` 헤더의 토큰으로 바꿉니다. 헤더가 없으면 팀 A 팀원입니다.

| 계정 | 토큰 | 볼 수 있는 프로젝트 |
|---|---|---|
| 팀 A 팀원 (기본) | `demo-token-team-a` | 결제 API, 사내 포털 |
| 팀 B 팀원 | `demo-token-team-b` | 배치 서버 |
| 보안 담당자 | `demo-token-security` | 전체 |

시연 순서 예: 서버 실행 → 조회 질문 → 등록("사내 포털에 OpenSSL 3.0.6 등록해줘" → "1번으로 확정해줘") → 보안 담당자로 "지금 검색 실행해줘"(T1 알림) → 검색 주기 창에서 데이터 시점을 T2로 변경 → 다시 "지금 검색 실행해줘"로 달라진 건만 알림이 나가는지 알림함에서 확인. 명령으로는 `python -m src.scheduler --snapshot T1`, `--snapshot T2`.

- LLM 채점은 리포트의 답변과 나란히 사람이 확인합니다. Nova Pro는 구조화 출력의 한글이 깨지기도 해서(판정 이유 문장) 판정 이유는 참고만 합니다.

**채점 기준**: "기대 ID 외의 추가 ID를 허용하면 해당하지 않는 취약점을 함께 알려 줘도 통과한다"는 피드백을 받아, 해당 여부와 조건 조회 문항 8건(1, 2, 3, 4, 15, 16, 17, 18번)과 28번은 답에 나온 CVE·GHSA ID가 기대 목록과 정확히 같아야 통과합니다. 두 회차 모두 이 기준으로 채점했습니다.

인-아웃 세트와 별도로, 알림 규칙은 두 시점 고정 데이터로 자동 테스트합니다(`tests/test_alert_rules.py`, `tests/test_alert_sources_failures.py`). 알림 누락 0건, 중복 0건, KEV 신규 등재 시 재알림 1회, 점수가 없던 건의 나중 알림, 조회 실패 뒤 재처리, 2회 연속 실패 통지를 확인합니다.

## 트라이앤에러 회고

**시도했지만 실패한 접근 · 왜 실패했는가**

- **모델이 가린 이름을 그대로 돌려줄 것이라 기대함**: 프로젝트명을 `[프로젝트3]`으로 가려 보냈더니 모델이 대괄호를 빼고 `프로젝트3`으로 도구를 불러 프로젝트를 찾지 못했습니다. 대괄호가 없어도 원래 이름으로 되돌리도록 고쳤습니다.
- **모델이 앞선 요청을 기억할 것처럼 등록을 설계함**: 요청마다 대화가 새로 시작되는데, "1번으로 확정해줘"를 받은 모델은 후보를 제시한 적이 없다고 보고 도구를 부르지 않았습니다. 후보는 서버에 저장돼 있으니 번호를 고르면 항상 확정 도구를 부르라고 프롬프트에 적어 해결했습니다. Nova Pro에서는 확정 도구는 부르지만 답에 제품 이름을 빠뜨려(1차의 9번), 도구의 안내 문장에 등록한 항목을 넣어 해결했습니다.
- **비슷한 결과를 주는 도구 두 개를 구분 없이 둠**: 해당 여부 조회와 현황 조회가 둘 다 프로젝트의 취약점 목록을 돌려줘서, 모델이 질문과 다른 도구를 고르거나(1번) 현황만 보고 스스로 판단해 답했습니다. 뒤의 경우 답은 맞았지만 '근거 없음' 판정을 내는 도구를 거치지 않아 라벨이 틀렸습니다.
- **모델이 도구 인자를 설명대로 채울 것이라 기대함**: Nova Pro는 `vuln_id`에 "mp4 모듈 관련" 같은 글을, `project`에 `"전체"`나 `.`을, 질문에 없는 프로젝트 이름을 넣었습니다(1차의 28, 19번과 고치는 중의 7번). 프롬프트에 규칙을 더해도 되풀이돼서, 도구가 인자를 검사해 바로잡거나 확인 순서를 바꾸는 코드로 막았습니다.
- **영어 설명문을 한글 질문으로 키워드 검색함**: 초기 25건 평가에서 문서 검색 도구가 한 번도 불리지 않았고, "HTTP/2 요청을 빠르게 취소해서 서버를 마비시키는 취약점"처럼 ID 없는 한글 질문은 키워드 검색으로 찾지 못했습니다. 모델이 한글 검색어를 영어 키워드로 넓히고, 의미 검색을 더해 두 순위를 합치는 하이브리드로 바꿨습니다. "SSH 서버의 로그인 시간 초과" 질문은 키워드 검색 상위 5건에 정답이 없었지만 의미 검색이 1위로 찾았습니다.
- **데이터에 없는 ID로 검색해도 문서가 나옴**: "CVE-2099-99999는 어떤 취약점이야?"에 모든 문서에 있는 "cve" 같은 단어 때문에 엉뚱한 문서가 나왔습니다. 질문의 ID를 하나도 찾지 못하면 '확인할 수 없음'으로 처리합니다.
- **최신 ragas를 그대로 설치하려 함**: 의존 패키지 하나(scikit-network)가 Python 3.14에서 빌드되지 않았고, ragas가 `langchain-community`에서 삭제된 모듈을 불러와 실패했습니다. 그 패키지만 빼고 설치하고, 삭제된 모듈 자리에 빈 클래스를 끼워 넣어 해결했습니다.

**최종 채택한 접근 · 왜 그것으로 갔는가**

- **판정은 코드, 문장은 모델**: 버전 비교와 알림 여부는 틀리면 안 되고 매번 같은 답이 나와야 해서 일반 코드로 만들었습니다. 덕분에 1차와 2차 평가에서 판정이 틀린 문항은 없었습니다.
- **라벨도 코드가 결정**: 도구가 접근을 거절했거나 거절 도구가 불렸으면 `guardrail`, 근거 없음 결과만 있으면 `no_answer`로 고정합니다. 모델이 다른 팀 데이터를 "보여 주겠다"고 답해도 실제 데이터는 도구가 주지 않습니다.
- **평가셋과 데이터를 코드보다 먼저 작성**: 등록 버전에는 해당하지 않는 취약점 4건을 일부러 넣어, 무조건 해당한다고 답하는 구현이 통과하지 못하게 했습니다.
- **모델이 자주 틀리는 곳은 프롬프트보다 코드로 막기**: 1차 실패 6건 중 5건을 도구와 미들웨어, 채점 스크립트의 코드로 고쳤고 프롬프트에만 기댄 것은 1번뿐입니다. 고칠 때마다 가짜 모델 테스트를 더하고 30건 전체를 다시 돌려 다른 문항이 깨지지 않는지 확인했습니다.

**남은 한계 · 향후 개선 방향**

- 현황 조회 답변의 근거인 프로젝트 등록 목록은 `contexts`에 싣지 않습니다. 그래서 현황 문항의 RAGAS 점수가 낮습니다. 등록 목록에는 프로젝트명이 들어 있어 평가 모델에 보내기 전에 가려야 하므로 이번에는 넣지 않았습니다.
- 라벨이 모델의 도구 선택에 기댑니다. 모델이 도구를 부르지 않고 "확인할 수 없음"이라고 답하면 라벨이 `answer`로 남습니다.
- 취약점 데이터는 고정 사본 20건이고, 실시간 NVD/OSV 조회와 오탐 교정은 만들지 않았습니다. 실제 메일 발송도 하지 않고 DB에 저장해 화면 알림함에서 봅니다.
- CVE가 없는 GHSA 사례는 여섯 제품에서 실제 항목을 찾지 못해 교육용 가상 항목 1건으로 대신했습니다.
- 쿼리 확장 키워드에 "vulnerability", "exploit" 같은 일반 단어가 섞여 키워드 검색에 잡음이 생깁니다. 리랭킹도 하지 않았습니다.
- Nova Pro는 도구 선택, 도구 인자, 도구 호출 형식, 구조화 출력(채점)이 불안정합니다. 인자 검사와 재시도로 막았지만 모델 판단에 달린 부분(1번의 도구 선택, 28번의 문서 검색 호출)은 실행마다 달라질 수 있습니다. 콘텐츠 필터 차단은 두 번 다시 불러도 막히면 그 문구가 그대로 답으로 나갑니다. 모델을 바꿀 때마다 평가를 다시 돌려야 하고, LLM 채점은 답변 모델과 따로 정하는 편이 낫습니다.
- 도구 실행 잠금은 한 요청 안에서만 겁니다. 여러 요청이 동시에 들어오면 같은 DB 연결을 함께 쓰는 문제는 남아 있습니다(로컬 시연에서는 한 사람이 씁니다).
- 요청 사이의 대화를 기억하지 않습니다. 등록 확정만 서버에 저장한 대기 후보로 이어집니다.
- 2차 평가는 한 번 실행한 결과이고, 같은 30건을 보며 고쳤습니다. 모델 응답의 편차와 처음 보는 질문에서의 성능은 반영되지 않았습니다.
